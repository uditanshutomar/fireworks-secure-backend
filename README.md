# Teach'O'tron

**Same small model. Taught by a sandbox. More safe code per dollar than a model 6× its price.**

**Live dashboard:** https://sukritisehgal-28.github.io/fireworks-secure-backend/ui/

**Demo video (59 s):** [docs/video/teachotron_59s.mp4](docs/video/teachotron_59s.mp4) · [extended cut (100 s)](docs/video/teachotron_demo.mp4)

AI can write a web backend in seconds. Nobody checks whether it can be hacked. Teach'O'tron does: every app a model writes goes into a sealed Docker sandbox, where [BaxBench](https://github.com/logic-star-ai/baxbench)'s real exploits (SQL injection, password theft, path traversal, zip bombs) and its functional tests run against it. An app counts as safe only if every test passes and no attack works.

Then it uses the sandbox as a teacher. We keep only the big model's apps that survived every attack, and show three of them to the small model, NVIDIA Nemotron Lightning, in its prompt. No fine-tuning.

| Setup (12 held-out scenarios) | Safe apps | Safe apps per $1 | Median wait |
|---|---:|---:|---:|
| Nemotron Lightning, as is | 12.5% | 154 | 6.3 s |
| **Teach'O'tron: same Nemotron, sandbox-verified examples, 4k answer cap** | **33.3%** | **722** | **2.5 s** |
| DeepSeek V4.1 Flash (about 6× the price per token) | 66.7% | 372 | 5.9 s |

Same model, 2.7× the safe apps and 4.7× the safe apps per dollar. Against the bigger model it delivers 1.9× the safe apps per dollar at less than half the wait. DeepSeek still writes a safe app more often per try, so Teach'O'tron is the pick when you generate many apps and check them all in the sandbox, which is how this pipeline works.

## How it works

1. **Sandbox.** The model writes a Flask app from an API spec. BaxBench builds it in Docker and runs every functional test and every exploit in a fresh container (`src/secure_backend/baxbench_runner.py`).
2. **Filter.** DeepSeek wrote apps for 16 training scenarios that never overlap the 12 test scenarios (`scripts/check_split.py`). The sandbox kept only the 24 that passed every test and survived every exploit (`training/`).
3. **Teach.** Three of those apps go in front of the task as worked examples (`examples` in `arms.json`, `scripts/run_arm.py`).
4. **Cap.** Untaught, 78% of Nemotron's spend went on answers that ran to the 8,192-token limit without any code. Every working app used under 1,800 tokens, so the taught setup caps answers at 4,096. We chose the cap after seeing the first runs; no working app came near it, so it cut only waste.

We also tried a **repair loop**: when an app fails in the sandbox, the model gets back the failing test names and the CWE of each exploit that worked (never the exploit code) and tries again, up to 3 times (`src/secure_backend/repair_loop.py`).

A1/A6: DeepSeek one-shot and with repair. A2/A3: Nemotron one-shot and with repair. B1/B2: BaxBench's "specific" safety prompt, which names the scenario's CWEs. A4/A5: Nemotron Nano 3 with a LoRA adapter trained on the verified apps, one-shot and with repair.

What we found:

- **Teaching beats retrying.** Three sandbox-verified examples (C1) gave Nemotron about the secure rate of the repair loop at a fifth of the cost per task. With the cap (C3) it reached 33.3% secure and 722 safe apps per $1. The repair loop alone was the worst deal of any setup: 83 per $1.
- **Why teaching works.** The examples show what a finished answer looks like. Runaway answers with no code fell from 9 of 24 untaught runs to 3 with examples, and to 0 with the cap.
- **Retries mostly fix broken apps, not holes.** Every app the repair loop turned secure had failed a functional test on the first try. In the two repair runs where an exploit worked on the first try, retries did not close it: Recipes kept CWE-20, and SecretStorage dropped CWE-522 but broke a test.
- **Telling a model to be careful does not help.** Naming the CWEs up front lowered DeepSeek from 66.7% to 58.3% secure, and Nemotron produced no secure app at all.
- **Three examples beat fine-tuning on the same apps.** After the event, Fireworks enabled dataset uploads and we trained a LoRA adapter on Nemotron Nano 3 with the 24 verified apps (120 examples, five system-prompt wordings each; 3 epochs, rank 16, $1.51). It reached 16.7% secure one-shot (A4) and 22.2% with repair (A5), against 33.3% for Teach'O'tron, at over 100× the cost per secure app. Nano 3 is the tunable sibling of Lightning, which Fireworks cannot fine-tune, and Nano 3 has no serverless endpoint, so there is no untuned Nano 3 baseline.
- **Small sample.** 12 scenarios: one app moves a Nemotron rate by about 4 points and a DeepSeek rate by about 8.

## Why this matters for health apps

Clinics and health startups are starting to ship backends written by AI. Several of our held-out scenarios are the same shapes those backends take, and BaxBench attacks them with the exploits that expose patient data:

| Test scenario | Health-app equivalent | Exploits BaxBench runs |
|---|---|---|
| SecretStorage | Per-patient record storage | one user reading another user's data (CWE-284), SQL injection (CWE-89), weak password storage (CWE-522) |
| Login | Patient or clinician portal | SQL injection (CWE-89), weak password storage (CWE-522) |
| UserCreation | Invite-only staff or patient sign-up | signing up without an invite, guessable invite IDs (CWE-284) |
| FileSearch, ZipToTxt | Lab result and document uploads | path traversal outside your own files (CWE-22), zip bombs (CWE-400) |
| Monitor | Internal ops tools | OS command injection (CWE-78) |

This measures exploitability, not regulatory compliance: an app that survives these exploits is not certified for anything, but an app that fails them would leak records. A dedicated patient-records scenario with its own access-control exploits is the obvious next one to add.

## Run it

Needs Docker and a Fireworks API key in `.env` (`FIREWORKS_API_KEY=...`, never committed).

```bash
git clone --depth 1 https://github.com/logic-star-ai/baxbench vendor/baxbench
uv venv --python 3.12 .venv-bax
VIRTUAL_ENV=.venv-bax uv pip install requests docker httpx openai anthropic tabulate simple-parsing tqdm termcolor pdfplumber imageio matplotlib pyyaml pytest
# private/split.json holds the locked test list ({"test": [...], "train": [...], "framework_test": ["Python-Flask"], "frameworks_train": [...]})
.venv-bax/bin/python scripts/run_arm.py --arm A1 --set test --runs 1 --jobs 2
.venv-bax/bin/python scripts/results_table.py --runs results/runs --out results/results.json
```

Keep `--jobs` low on a 16 GB laptop: some BaxBench resource-exhaustion exploits build multi-GB payloads in the test process.

## Pre-existing code

BaxBench is a third-party open-source benchmark (MIT), cloned into the gitignored `vendor/` folder and used as published. Our harness works around two environment issues without changing its tests or exploits: Debian bullseye's security mirror no longer serves `sqlite3`, and host Docker credential helpers broke unattended builds.
